# Полная локальная копия данных Explorer

`scripts/backup_payloads.py` — отдельная инженерная утилита `ENGINEERING_GLUE`. Она дополняет metadata backup и сохраняет **сами файлы**, включая веса, optimizer/checkpoint, RGB, NPZ, Parquet, записи и CAD-меши. Расширения не исключаются. Исходники, сервисы, настройки контроллера, калибровки и устройства не изменяются. Сеть и SSH утилита не использует.

Из выбранного центрального `data_dir` копируются целиком ровно шесть папок: `jobs`, `datasets`, `episodes`, `artifacts`, `assets`, `qualification`. Отсутствующие папки явно перечисляются. Пустые папки сохраняются. Другие локальные папки, файлы, оставшиеся только на Pi/Nano, checkout, виртуальные среды и ОС не входят в эту копию. Для восстановления всего диска нужны отдельные копии этих частей. Наличие центрального архива не доказывает сохранность удалённых оригиналов.

Все задания центральной БД должны иметь статус `completed`, `failed` или `cancelled`. `queued`, `paused`, неизвестный статус и любое незавершённое задание означают отказ. На время копирования оператор не создаёт новые задания, не ведёт запись и не меняет исходные файлы. Утилита читает и сравнивает полный digest строк `jobs` до, во время и после копирования. События могут поступать; при этом metadata содержит свой согласованный снимок БД на обозначенный момент, а не все последующие события. Очередь и сервисы не останавливаются и блокировкой на весь срок не удерживаются.

`source_window` содержит начало/конец окна, время metadata snapshot, digest/count/statuses заданий и явные `atomic_filesystem_snapshot=false`, `cross_host_atomic=false`. Это проверенное окно локальных исходников, **не атомарный снимок файловой системы и не одновременная копия трёх устройств**. Изменение задания или дерева файлов во время окна приводит к отказу; изменения после закрытия окна относятся к следующей копии.

## Создание на Homebrain

Нужно свободное место примерно для **двух полных объёмов payloads** плюс metadata и запас: одна постоянная копия и вторая временная для реального восстановления. Чтение выполняется несколько раз: потоковое копирование, финальный SHA исходников, проверка backup и независимое чтение восстановленных файлов. Большая коллекция кадров занимает время. Границы утилиты: до 500 000 исходных членов дерева, metadata по существующим ограничениям, manifest до 256 MiB. Выход за границу не замалчивается.

Папка назначения должна быть новой, с существующим родителем, вне live state, конфигурации, калибровок, checkout и существующей metadata-копии. Все пути разрешаются с учётом symlink. Не следует выбирать папку на том же SSD в качестве единственного экземпляра.

```sh
install -d -m 700 "$HOME/.local/state/explorer/full-backups"
PYTHONDONTWRITEBYTECODE=1 "$HOME/.local/share/explorer/venv/bin/python" \
  "$HOME/.local/share/explorer/current/scripts/backup_payloads.py" create \
  --destination "$HOME/.local/state/explorer/full-backups/full-20261026"
```

По умолчанию `data_dir` читается из `~/.config/explorer/config.json`; `--state` явно его заменяет. `--config` принимает папку частной конфигурации. Для отдельно подготовленных оригинальных калибровок Pi:

```sh
PYTHONDONTWRITEBYTECODE=1 "$HOME/.local/share/explorer/venv/bin/python" \
  "$HOME/.local/share/explorer/current/scripts/backup_payloads.py" create \
  --calibration "$HOME/.local/state/explorer/backup-staging/pi-original-calibration" \
  --destination "$HOME/.local/state/explorer/full-backups/full-with-staged-pi-20261026"
```

Внутри `metadata/` вызывается существующий `backup_state.create_backup`: SQLite копируется через backup API с committed WAL, сохраняются частные config/calibration, inventory среды/исходников и выполняется их изолированное восстановление. Живые `research.sqlite3`, `-wal`, `-shm` обычным файловым копированием не берутся; найденные hardlink с теми же inode в payload-папках тоже приводят к отказу. Можно добавить `--metadata-backup ПАПКА` для уже проверенной копии того же `source_state`; её полный snapshot строк заданий должен точно совпадать с текущими завершёнными заданиями. Это позволяет повторно использовать атомарный снимок SQLite, но не превращает события двух моментов в общий атомарный снимок.

У каталогов копии режим 700, у обычных файлов 600. Config/calibration содержат частные данные; секреты не печатаются. Внешние/broken symlink, symlink в корне любой из шести папок, FIFO/socket/device приводят к отказу. Внутренние ссылки разрешены только на существующий член этих шести папок; сохраняются как переносимые относительные ссылки, исходное значение записывается в manifest. Hardlink сохраняется независимой побайтовой копией, связь inode исходника отражена в inventory.

Каждый обычный файл читается через `O_NOFOLLOW`, копируется блоками, хешируется; сравниваются inode/device/size/mode/mtime/ctime до и после. Затем исходники полностью инвентаризируются повторно и перечитываются для SHA256. Замена файла, обрезание, изменение содержимого/дерева обнаруживаются. До завершения создаётся частный `receipt.json` с `completed=false`; при ошибке остаются частичные файлы, стадия отказа и тип ошибки. Они не являются готовой копией. Повторный запуск требует **новую** папку; удаление исходников или старых копий не выполняется.

## Проверка и реальное восстановление в новую папку

Обычная проверка перечитывает каждый файл, сравнивает точное дерево, размеры/SHA256, metadata и snapshot заданий:

```sh
PYTHONDONTWRITEBYTECODE=1 "$HOME/.local/share/explorer/venv/bin/python" \
  "$HOME/.local/share/explorer/current/scripts/backup_payloads.py" verify \
  --backup "$HOME/.local/state/explorer/full-backups/full-20261026"
```

`create` перед успешным завершением **реально восстанавливает всю копию** во временную соседнюю папку, независимо перечитывает SHA всех восстановленных файлов, открывает новый изолированный Store и сравнивает integrity/counts. Проверяются известные локальные ссылки/хеши Explorer NPZ/robot manifests, сохранённых оригиналов, LeRobot exports, checkpoint и artifact maps, в том числе в словарях/списках JSON. Абсолютные пути внутри исходного state и его исходного symlink-алиаса сопоставляются с изолированной копией. Весовые файлы/pickle не исполняются и не десериализуются. Исходные абсолютные provenance-пути других устройств остаются как свидетельства, учитываются отдельно и не выдаются за восстановленные удалённые файлы. Указания путей в исходных JSON не переписываются; это репетиция хранения, а не включение старых заданий в live scheduler.

Для отдельной повторной репетиции:

```sh
install -d -m 700 "$HOME/.local/state/explorer/full-rehearsals"
PYTHONDONTWRITEBYTECODE=1 "$HOME/.local/share/explorer/venv/bin/python" \
  "$HOME/.local/share/explorer/current/scripts/backup_payloads.py" restore \
  --backup "$HOME/.local/state/explorer/full-backups/full-20261026" \
  --destination "$HOME/.local/state/explorer/full-rehearsals/check-20261026" --apply
```

Без `--apply` восстановление ничего не создаёт. С `--apply` разрешена только новая явно выбранная папка вне защищённых источников, backup, runtime/config/calibration, checkout и старого `~/Explorer`. В ней будут `data/` с payloads и изолированной БД, `metadata/` с частными файлами и `restore-receipt.json`. Сервисы, `current`, реальные конфигурация/контроллер не переключаются. Уже существующая папка никогда не перезаписывается.

После переноса на другой носитель/компьютер нужно снова выполнить `verify`, затем отдельную реальную репетицию в новой папке. Папка копии может храниться в ignored private-каталоге Mac; папка репетиции должна находиться вне checkout. Копирование между хостами и факт второй копии оператор подтверждает отдельно — успешный локальный receipt не доказывает, что перенос состоялся.

Успех означает `completed=true`, `test_restore_passed=true`, `all_restored_file_sha256_verified=true`, число/байты payloads, общие число/байты файлов и `manifest_sha256`. SHA manifest позволяет сверить два экземпляра; это контроль целостности, не криптографическая подпись. Локальные тесты с искусственными файлами проверяют механизм, но **не являются свидетельством сохранения реальных данных NX**: такое свидетельство появляется только из фактического запуска на выбранном live `data_dir` и последующей проверки.
