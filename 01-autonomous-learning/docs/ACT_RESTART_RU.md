# Продолжение ACT после перезапуска процесса

Это ENGINEERING_GLUE вокруг официального LeRobot ACT, без изменения его модели
и функции обучения. Теперь `optimize_act` сохраняет действительную точку
продолжения: веса и buffers, AdamW, номер завершённого обновления и loss history,
Python/global NumPy/Torch CPU RNG, RNG всех уже инициализированных CUDA-устройств,
перестановку примеров, позицию в ней и отдельный generator этой перестановки.

По умолчанию сохраняются начальная точка, каждые **25** обновлений и финальная.
Payload сначала записывается во временный файл и fsync, затем атомарно
переименовывается; каталог fsync. Лишь после этого атомарно фиксируется
`act_resume/latest.json` с SHA256. Сохраняются две последние зафиксированные
версии. Незавершённая новая запись не подменяет прежнюю действительную точку.
Чужие файлы и symlink при уборке версий не удаляются.

На повторном входе проверяются SHA источников и checkpoint, source/settings/
implementation signature, модель/конфигурация, trainable-параметры, версии
Torch/torchvision/LeRobot/NumPy, precision/determinism flags и история обновлений.
Изменённые источники, число шагов, параметры, реализация или повреждённый файл
дают явную ошибку с сохранением прежней точки. Чтобы изменить постановку,
создаётся новое задание с новой lineage; старый checkpoint не обнуляется.

`EpisodeChunks` и `RecordedChunks` автоматически задают проверяемый контекст
источников. Запись не меняет исходные NPZ, manifest, калибровки или данные
других заданий. `preserve_interrupted_attempt` архивирует прежние производные
артефакты, сохраняя `act_resume`. Для повторного входа supervisor должен запустить
**тот же ID задания и pinned release**. Решения о retry/queue принадлежат
планировщику, а не функции оптимизации.

## Публичный контракт и пользовательские Dataset

Существующие аргументы и результат `(optimizer, losses, started)` сохранены.
Добавлены необязательные `resume_context=None, checkpoint_interval=25`:

```python
context = {
    "source_signature": immutable_provenance_sha256,
    "source_files": [
        {"path": "/absolute/immutable-source.npz", "sha256": expected_sha256}
    ],
    "label_semantics": "current-state teacher query, not executed student action"
}
optimizer, losses, started = optimize_act(
    policy, samples, settings, folder, update,
    resume_context=context, checkpoint_interval=25,
)
```

Без проверяемого контекста старый сторонний Dataset продолжает работать,
но `optimizer.explorer_resume_info.supported=false`; надёжное продолжение
для него не заявляется. Существующая точка не загружается с таким неопределённым
контекстом. Источник и порядок примеров должны оставаться неизменными.
Пользовательские собственные RNG/counters Dataset требуют парных
`resume_state_dict()` / `load_resume_state_dict(value)` с совместимыми с
`torch.load(weights_only=True)` примитивами/Tensor; стандартные адаптеры не
содержат таких скрытых случайных генераторов.

Межпроцессный lock допускает одного optimizer writer на каталог задания. Выбор индексов сохраняет порядок
прежнего `DataLoader(shuffle=True, generator=...)`; текущие adapters используют
однопроцессное чтение. Callback прогресса изолирован от случайной последовательности
обучения. В `training_resume` есть `resumed_from_step`, `completed_steps`,
`optimizer_steps_executed_this_process`, signature и active time.

После аварии обновления позднее последнего checkpoint могут вычислиться повторно.
Число `completed_steps` — история сохранённой модели, **не суммарная стоимость
всех неуспешных попыток**. Длительность worker attempt и активное время сохранённой
оптимизации различаются; простой оборудования не выдаётся за обучение.

## Граница симуляционного конвейера

Когда завершённый PPO teacher и исходный набор уже подготовлены, перед ACT
сохраняется `pilot_actor_source.json`. При повторном входе сохраняются их файлы,
проверяются SHA/settings/source pins и возобновляется ACT; учитель и dataset
не создаются повторно. Результат явно сообщает
`completed_teacher_and_dataset_reused=true` и `mid_ppo_optimizer_resumed=false`.

**Прерывание внутри PPO или до готовности teacher/dataset пока не поддерживает
продолжение его optimizer/collector.** Такой этап сохраняется как прерванная
попытка и запускается заново. Полное восстановление MuJoCo trajectory/collector,
PPO RNG и непрерывный physics replay этим изменением не заявляются.

## Действительно выполненные проверки

- Стохастический CPU Dataset использует Python, NumPy и Torch; модель использует
  dropout. Непрерывные 12 обновлений и 4 + restart + 8 дают побитно одинаковые
  веса, optimizer state и полную историю loss, включая позицию внутри эпохи.
- Искусственная ошибка между записью payload и заменой pointer оставляет старую
  действительную точку. Перезапуск с неё даёт тот же итог.
- Источник/settings/checkpoint tamper отклоняется без перезаписи прежней точки;
  исходный порядок DataLoader и глобальный Torch RNG проверяются отдельно.
- Настоящий официальный ACT с RGB, шестью осями и VAE: 4 обновления непрерывно
  и 2 + restart + 2 побитно совпадают по модели, AdamW и loss. Manifest/NPZ
  остаются неизменными; архивирование промежуточной попытки не удаляет checkpoint.
- Настоящий CAD/MuJoCo pilot: PPO 4096, исходные 12 эпизодов; ACT прерван после
  сохранённого обновления 25 и завершает оставшиеся 5. SHA учителя и всех исходных
  dataset-файлов совпадают до/после; повторно PPO не обучается.

Проверки Mac выполнены на Torch 2.14.1 / torchvision 0.29.1 вне заявленных верхних границ LeRobot 0.6.1; это измеренное исключение для данного теста, а не общая квалификация framework.

Доказательства/версии/исходные SHA сохраняются в
`research/experiments/act-resume-20261026/`. Эти CPU проверки не являются
сертификатом побитной эквивалентности CUDA kernels, физического навыка или H1–H5.
CUDA RNG восстанавливается, но конкретная GPU/runtime-пара проверяется отдельно;
недетерминированные kernels могут потребовать отдельно заданного numerical допуска.
