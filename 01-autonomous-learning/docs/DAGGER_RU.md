# Один цикл DAgger в MuJoCo

`explorer_sim.dagger.run_dagger(store, job)` выполняет настоящее обучение
официального LeRobot ACT и один цикл сбора поправок на состояниях ученика.
Используется существующий CAD reach-стенд: неподвижная виртуальная база,
три активных сустава, видимая зелёная цель. На устройства робот ничего не отправляет.

Метод адаптирован из [Ross, Gordon, Bagnell, 2011, §3 / Algorithm 3.1](https://proceedings.mlr.press/v15/ross11a/ross11a.pdf).
После исходного обучения на эксперте ученик действует сам (`beta=0`). Учитель
размечает посещённые им состояния; эти данные объединяются с исходными, затем
следует новый этап обучения. Один такой цикл не устанавливает теоретическую
гарантию DAgger, надёжное восстановление или успех задач с тканью/кухней.

## Вход и выход для интеграции

```python
result = run_dagger(store, {
    "id": "new-dagger-job",
    "config": {
        "source_job_id": "completed-sim-pilot-id",
        "seed": 52041,
        "initial_act_steps": 120,
        "act_steps": 120,
        "collection_episodes": 4,
        "evaluation_episodes": 6,
        "device": "cpu"
    }
})
```

`source_job_id` должен ссылаться на завершённый `sim_pilot`. Для отдельного
локального запуска вместо него допускается `source_result` — абсолютный путь
к исходному `result.json`. По умолчанию соседние файлы: `teacher_ppo.zip`,
`dataset/manifest.json`, `provenance.json`, `model.xml`. Их можно явно указать
через `teacher_checkpoint`, `dataset_manifest`, `source_provenance`, `source_model`.
Нужен исходный полный результат пилота, а не произвольная пара весов и картинок.
`mesh_dir` или `EXPLORER_SIM_MESH_DIR` указывает на проверенные реальные CAD-меши.

Артефакты находятся в `store.root/jobs/<id>`: `provenance.json`, исходная модель,
`round0_expert`, `corrections`, `round1_aggregated`, `development_before`,
`development_after`, `before.json`, `after.json`, `collection.json`, `result.json`.
Настоящий последний MuJoCo render сохраняется в `frame.jpg`; это изображение
симуляции. Функция сообщает фазу/прогресс через `store.update_job` и возвращает
результат. Она не добавляет физическую модель управления в реестр навыков и не
изменяет маршруты, очередь или интерфейс приложения.

## Что именно учится

Исходный учитель — сохранённый Stable-Baselines3 PPO. До любого шага среды
вызывается `teacher.predict(env.observation())` на текущем привилегированном
состоянии. Его три приращения преобразуются в ограниченную абсолютную команду
точно по правилам `ReachEnv`. Ради получения метки учитель среду не двигает.

ACT получает только RGB и нормализованную оценку предыдущей команды девяти осей.
Цель XYZ, реальные состояния MuJoCo и вход учителя в пакет ACT не попадают.
Команда ученика проходит существующее ограничение `step_command`; в трассе
отдельно сохраняются:

- `requested_action_normalized` — выход ученика до ограничения среды;
- `executed_action_native` — команда, действительно приложенная к виртуальным
  приводам после ограничения; это командная оценка, а не измеренная поза;
- `teacher_label_native` — контрфактическая подсказка учителя, которая не исполнялась;
- `teacher_observation` и времена симуляции — данные для проверки происхождения.

Поле `teacher_label_valid` означает корректную форму, конечные числа и запрос
на текущем состоянии. Оно не означает проверенный успешный ремонт траектории.
Реальное восстановление веткой учителя из каждого ошибочного состояния не
выполнялось. Успех учителя на отдельно сброшенных сценах проверяется отдельно.

Из старых эпизодов допускаются только явные `outcome.success=true` в training
split. Неудачные и неизвестные экспертные траектории сохраняются, но их действия
не становятся целями BC. Для новых траекторий важна метка учителя: неудача ученика
не удаляет корректные запросы. Собственные действия ученика не используются как
экспертные цели.

В `DaggerSamples` обучение использует только текущую метку: остальные позиции ACT chunk
помечены padding. То же правило применяется к старым экспертным примерам.
Позднейшая подсказка в другом состоянии ученика не выдаётся за продолжение
экспертной траектории из текущего состояния. Исполняется одна команда за решение.
Используются публичный API ACT, Torch AdamW и официальные методы сохранения /
повторной загрузки ACT; собственная реализация нейросети не подставляется.

Формат `explorer_dagger_teacher_queries_v1` намеренно отличается от обычных
эпизодов исполненных демонстраций. Его нельзя передавать generic export/BC как
обычную запись: там нет подменяющего смысл поля `action_native`/`command9`.
Общий экспортёр отказывает для таких данных. В этом коммите общий формат
датасетов не меняется.

## Разделение и сохранность

До обучения записывается план seeds. Сбор и development-проверка не пересекаются
друг с другом, исходными demonstration seeds, исходной проверкой учителя и
исходной reload-проверкой. Наблюдения из `development_before/after` не добавляются
в Dataset. До и после исполняются одинаковые development-сцены, без обучения
на их наблюдениях. Закрытого финального теста здесь нет.

Проверяются SHA учителя, всех исходных эпизодов/метаданных, CAD-мешей и кода модели;
структура XML должна совпадать с исходным стендом. Нормализация и причинная связь
команд исходных демонстраций проверяются. Оригиналы не перезаписываются; SHA
повторно сверяются после сбора и после обучения.

Повторный завершённый запуск проверяет источник/настройки/план/код и SHA всех
собственных неизменяемых артефактов. Он возвращает прежний результат без новых
шагов оптимизации. Незавершённая попытка сохраняется в `interrupted_attempts`,
новая начинается заново; DAgger сам не заявляет возобновление optimizer с середины
раунда. Активные worker-логи не перемещаются и не включаются в неизменяемую сумму.

## Реальная development-проверка 26 октября 2026

Учитель и 12 исходных эпизодов взяты из завершённого `default-pilot-v1`.
Для BC использованы 47 кадров из 10 успешных эпизодов; `episode_0008/0009`
исключены. Исторический ACT этого пилота не загружался: начальный ACT заново
обучался только на допустимых экспертных примерах.

Оба запуска: seed `52041`, сбор `54041..54044`, проверка `62041..62046`, horizon
60, RGB 64×64, chunk 8 с одной валидной меткой, batch 8, CPU. Старый критерий
успеха сохранён: расстояние <0,025 м в трёх последовательных решениях.

| Запуск | ACT до / после сбора | Успех до → после | Средняя конечная дистанция до → после |
|---|---:|---:|---:|
| `dagger-cpu-development-v3` | 120 / 120 updates | 0/6 → 0/6 | 0,09664 → 0,08184 м |
| `dagger-cpu-development-tuning480-v1` | 480 / 480 updates | 0/6 → 2/6 | 0,07717 → 0,07317 м |

Первый запуск сохранён с отрицательным результатом по основной метрике. Второй
был явно запрошенным development-подбором продолжительности обучения после
этого результата. В нём 240 запросов учителя из четырёх неудачных попыток ученика
вошли в обучение; первый запуск содержал 127 запросов, включая 120 из неудачных
попыток. Учитель отдельно достиг 6/6 в обоих запусках. Веса ACT реально менялись
на обоих этапах, сохранение/повторная загрузка совпали с max error 0.0. Проверка
повторного вызова не изменила артефакты.

Двух успехов из шести недостаточно для заявления о надёжности. Отдельного
контроля с таким же числом дополнительных BC updates без агрегации не было,
поэтому причинный эффект именно новых данных не выделен.

Точные SHA и результаты — в `DAGGER_DEVELOPMENT_VALIDATION.json`. Полные NPZ,
чекпойнты и optimizer-файлы обоих запусков отдельно скопированы с проверкой SHA
в приватный каталог проекта `_registry/private/engineering_runs/dagger-20261026`;
исходники в `/tmp` также сохранены. Публикации весов/данных не выполнялось.

Среда: MuJoCo 3.17.0, SB3 2.9.0, LeRobot 0.6.1, Torch 2.14.1, torchvision 0.29.1.
Последние две версии выходят за объявленные верхние границы LeRobot 0.6.1;
эта совместимость проверена только данным конкретным выполнением. Python также
сообщал о дублирующихся AVFoundation-классах библиотек cv2/av; оба запуска
завершились, но квалификация всего окружения этим не установлена.
