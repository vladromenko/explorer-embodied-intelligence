# Полный контактный перенос в MuJoCo

`explorer_sim.manipulation.run_manipulation(store, job)` запускает отдельную задачу
`candy_to_tray` либо `sock_to_basket`. Это новая задача переноса всего предмета;
прежний `sim_pilot` остаётся отдельным экспериментом reach.

```json
{"kind":"manipulation","project_id":"01","config":{"task":"sock_to_basket","teacher_steps":1024,"horizon":600,"evaluation_episodes":2,"device":"cpu"}}
```

Центральный обработчик задания вызывает эту функцию и сохраняет возвращённый
результат. Регистрация API/очереди выполняется интегратором отдельно. `mesh_dir`
либо `EXPLORER_SIM_MESH_DIR` указывает на проверенные исходные CAD STL. Функция
не открывает SSH/ROS/serial и не обращается к физическому роботу.

## Что действительно моделируется

Сохраняются все 20 CAD meshes, исходные URDF origin/axis/inertia, шесть осей
привода, mimic-связи захвата, противолежащие контактные подушечки и конечный
момент servo. Контактные оболочки, трение, материал и динамика приводов —
оценки исходной модели; их точность на оборудовании не установлена.

Основание закреплено явно записанным weld в симуляции. Для ограниченного
локального переноса предмет начинается в 20 см перед основанием; цель —
поднос/корзина сбоку. Это **не полный мобильный маршрут по кухне**.

Конфета — отдельный свободный жёсткий объект с упаковкой, массой 12,6 г и
явно заданной геометрией; старое печенье не переименовывается в конфету.
Носок — свободная открытая трубка с зашитым мыском: 57 вершин, 104 треугольника,
2D flex с изгибом, физическим контактом и самостолкновением. Нет привязки ткани
к пальцам, pin/weld предмета, телепортации или жёсткой замены ткани.

Новая задача удаляет только устаревший `flexcomp/contact internal` из
полученного XML. Его удаление соответствует [изменению MuJoCo 3.15](https://mujoco.readthedocs.io/en/stable/changelog.html#version-3-15-0-october-5-2026)
и [первичному изменению исходников](https://github.com/google-deepmind/mujoco/commit/5023a4a50).
Остальные параметры ткани сохраняются. Старый builder не редактируется.

## Выполнение и оценка

Управляющий период — 50 мс, физический шаг — 2 мс. Запрос сети сохраняется
**до** ограничения. Исполнитель ограничивает нормализованные приращения,
диапазоны servo и скорость исходного streaming-профиля; по физическим
подшагам интерполируется только `ctrl`, после reset `qpos` не подменяется.
Это заявленный простой профиль симуляции, а не обещание parity с аппаратным
Ruckig/MCU исполнителем. Команды основания во всех данных равны нулю.

Отдельный `FullTaskEvaluator` на каждом физическом подшаге извлекает реальные
нормальные силы через [mj_contactForce](https://mujoco.readthedocs.io/en/stable/APIreference/APIfunctions.html#mj-contactforce).
Для успеха нужны последовательно:

1. Двусторонний контакт пальцев не менее 80 мс.
2. Подъём среднего уровня предмета на 45 мм с двусторонним контактом не менее 200 мс.
3. Перенос всего объекта внутрь проекции цели, выше края, при сохранённом контакте.
4. Полное размещение внутри; реальная опора на дно; открытый захват без контакта
   пальцев; максимальная скорость точек менее 0,05 м/с не менее 500 мс.

Для ткани проверяются все фактические flex-вершины. Для жёсткого объекта
используется консервативный набор углов охватывающих параллелепипедов всех
контактных геометрий; скорость учитывает и вращение через
[mj_objectVelocity](https://mujoco.readthedocs.io/en/stable/APIreference/APIfunctions.html#mj-objectvelocity).
Названия фаз планировщика и его прогнозы не определяют успех.

Сначала исполняется отдельно подписанный `scripted_truth_ik_baseline`, затем
с нуля обучается поддерживаемый SB3 PPO. Сеть PPO получает истинное состояние
симуляции; её действия не подменяются планировщиком. Счётчик hook фактически
считает optimizer.step, отдельно записываются эпохи SB3 и timesteps. Checkpoint
сохраняется, загружается заново и выполняется на заранее объявленных независимых
development seeds. Успех планировщика не считается успехом PPO и не становится
ложной успешной демонстрацией PPO. Визуальный ACT student для этих новых задач
ещё не реализован; result явно хранит это ограничение.

Во время обучения `training-action-requests.jsonl` отдельно сохраняет Gaussian
sample до внутреннего clipping SB3, результат clipping, исходный командный state
и фактический servo endpoint. При независимой детерминированной оценке напрямую
извлекается unclipped mean распределения policy: обычный `model.predict` уже
скрывает raw значения вне Box, поэтому для такой записи не используется.

## Данные и воспроизведение

Каждая неизменяемая попытка расположена в `jobs/<id>/attempts/<uuid>`; предыдущие
незавершённые попытки не удаляются. Итог в `jobs/<id>/result.json` содержит хеши
всех файлов. Повторный вызов с теми же исходниками/параметрами возвращает
проверенный результат; повреждённые файлы или другая реализация отвергаются.
Исходные модули/URDF/SRDF/профиль сохраняются в `implementation_sources` и
проверяются на дрейф в конце запуска.

`trajectory.npz` сохраняет реальные RGB до действия, `state_command9`, исходный
запрос `raw_requested_action6`, запрошенный endpoint, действительно переданный
simulator servo endpoint, точки предмета отдельно для оценки, исходные времена
симуляции и полное native состояние `mjSTATE_INTEGRATION` (T+1 состояний).
Это [полное состояние интеграции](https://mujoco.readthedocs.io/en/stable/APIreference/APItypes.html#mjstate),
включая control, warm start и пользовательские силы, а не только qpos.
`substep_contact_trace` имеет T×25 строк и столбцы:

`sim_time_s, left_force_N, right_force_N, bottom_support_N, center_x_m,
center_y_m, center_z_m, min_z_m, max_z_m, max_point_speed_m_s`.

`final.jpg` рендерится отдельно после последнего действия с явным
`final_image_sim_time_s`; он не подменяется предыдущим pre-action кадром.

`replay_trajectory` восстанавливает только исходное полное состояние, затем
заново выполняет все запросы и сравнивает каждое полученное native состояние.
Предмет не перемещается по сохранённым кадрам. Нулевой остаток доказывает
детерминированное воспроизведение этой конкретной модели/среды, а не физическую
точность модели на роботе.

Измерение 1/2/4 независимых процессов выполняет настоящие физические подшаги,
пишет CPU time, ru_maxrss, throughput с учётом spawn и без него. Это benchmark
сред, **не параллельное обучение**; фактический PPO использует один worker.
Температура не измеряется, перенос результата Mac на NX не подразумевается.

Фактические числа и неизменяемые пути проверки: `MANIPULATION_VALIDATION.json`.
Ни успешный планировщик, ни малая development-выборка не присваивают готовность
физическому навыку, обобщение, sealed validation или научную новизну.
