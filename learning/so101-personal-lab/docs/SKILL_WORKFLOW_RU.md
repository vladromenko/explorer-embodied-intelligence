# Эксперимент 06: от показов к офлайн-модели

`explorer.lab_skill_workflow` хранит предложения SkillSpec, подтверждение версии,
сессии, привязки оригинальных эпизодов и разборы фаз отдельными неизменяемыми
событиями Store. Он не запускает телеприсутствие, запись, камеры или приводы.
`capture_context()` возвращает только метаданные для существующего native
`record/start`. Разные действия пользователя сохраняют исходный SkillSpec,
сцену, сессию, экземпляр предмета и буквальный train/development/sealed_test.

Один навык содержит все его принятые оригиналы. Начальный технический план:
три разных учебных условия, отдельная проверка и закрытая сессия. Пять показов
не означают освоенный навык. Исходные scene/session/object/frame identities
и SHA JPEG не пересекаются между выборками. Старый hold, неизвестный исход,
неполные leader/requested/accepted/dispatched/measured данные, недействительные
маски, неподтверждённые часы и отсутствующий разбор всего видео остаются для
анализа. Пересмотр разбора создаёт новое событие и снимает готовность старого
агрегата. Байты исходных записей не исправляются и не переписываются.

Оператор явно отмечает наблюдавшиеся фазы, видимость предмета/цели и исход
показа. Это источник целевых BC-команд, а не проверка выученной модели.
Индексы фаз покрывают точную исходную последовательность кадров. Запрошенные,
принятые, отправленные команды и измеренное состояние последователя различны;
host-write receipt не означает MCU acknowledgement, контакт или достижение.
Нулевые действительные координаты сохраняются. Моторные калибровки и камера
идентифицируются по фактическим источникам. Метрическая калибровка стола/камеры
остаётся отдельным условием геометрического физического исполнения; её отсутствие
не запрещает корректный RGB + измеренный follower6 ACT-показ.

`build_aggregate()` под блокировкой экспортирует все принятые train/development
оригиналы через существующий station adapter и настоящий официальный
LeRobotDataset 0.6.1, вызывает finalize и проверяет чтение всех кадров,
состояний и действий. Закрытые данные представлены ссылками/SHA без их payload.
Внешний манифест связывает SkillSpec, операторские sidecars, внутреннее точное
представление, официальный Dataset и SHA каждого артефакта. Смена исходника,
обзора или содержимого агрегата снимает готовность. Hub не используется.

`explorer_sim.so101_skill_training.run_so101_skill_train(store, job)` принимает
только `so101_skill_train`, project 06, CPU и зафиксированный внешний SHA.
Он обучает официальный ACT: RGB + measured follower6 → dispatched follower6,
использует существующие неизменённые нормализованные диапазоны первых пяти
суставов [-100,100], gripper [0,100], выполняет настоящие AdamW updates,
сохранение/повторную загрузку и офлайн-ошибку на development chunks. Текст задачи
остаётся метаданными. Этот путь не импортирует официальный hardware robot и
не вызывает replay CLI. Его стандартный use_degrees=True несовместим с native
контрактом; для последующего отдельного исполнения требуется существующий
native executor и подтверждённое use_degrees=False отображение координат.

Store.add_skill получает полную карточку с SHA весов/набора, исходными IDs,
контрактом и пределами проверки. Синтетическая программная квалификация имеет
source_kind/source_type SIMULATION и deployment_scope SIMULATION_ONLY.
Настоящие обученные записи остаются OFFLINE_SHADOW_PENDING_SEPARATE_OBSERVED_TEST.
Ни один результат потерь или разбора демонстрации не разрешает движение.

## Подключение

В основном FastAPI после общей auth/CSRF middleware:
`lab_skill_api.install_router(app, lambda: STORE)`.
Маршруты имеют префикс `/api/lab/skills`:

* GET `/catalogue`, `/imports`, корень, `/{id}?version=N`, `/{id}/readiness`;
* POST корень — предложение; POST `/{id}/revision`, `/confirm`, `/session`,
  `/capture-context`, `/bind`, `/review`, `/aggregate`, `/train` — явная версия;
* GET `/imports/{job}/review?after=0&limit=100` — исходная временная шкала;
* GET `/imports/{job}/frame/{index}` — исходный проверенный JPEG без новой камеры.

Root scheduler должен считать `so101_skill_train` тяжёлой CPU-задачей и вызывать
указанный learner из runner. Здесь runner/scheduler/app не изменяются.
Пауза/перезапуск пользуются существующим durable optimizer checkpoint с
зафиксированными source/settings/implementation signatures. Изменение кода
не перетирает старый checkpoint и требует явного нового job. Отмена проверяется
при progress callbacks; физического executor в этой задаче нет.

## Фактическая квалификация 2026-10-26

Временные software-fixture originals: 5 × 8 JPEG, native6, отдельные IDs,
сессии, сцены, предметы и исходные split. Реальный официальный Dataset:
4 train/development эпизода, 32 кадра; закрытые 8 кадров не экспортируются.
ACT прошёл 8 CPU updates, loss 1.107820 → 0.293283, изменённые веса,
save/reload max error 0.0. Проверены Store-карточка SIMULATION_ONLY,
блокировка shadow/physical и снятие trained readiness при подмене checkpoint.
Receipt: `ACT6_WORKFLOW_QUALIFICATION.json`. Это не симуляция физики и не
физическая попытка. Успех переноса конфетки/другого предмета не заявляется.

Обычные тесты: `pytest -q tests/test_lab_skill_workflow.py` (11 pass,
реальное обучение специально пропускается). Для отдельной явно выбранной
малой квалификации установить `EXPLORER_RUN_06_OPTIMIZER=1`; этот тест создаёт
новый временный Dataset/model, поэтому не следует повторять его как polling.
