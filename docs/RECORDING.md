# Запись и аппаратный контракт

`RecordingManager` работает на сервере и не зависит от открытой вкладки. Источник `synthetic_test` создаёт исключительно технические данные; его joints/actions помечены `valid=false`, а датасет `test_only=true`. Такие данные не доказывают исправность камер, шины или захвата и не входят в обычное обучение.

Рабочий процесс: создать датасет с произвольным отображаемым именем и текстом задачи → Start → End → Next. Re-record сохраняет отвергнутую запись в quarantine и исключает её из состава train. Stop завершает текущий непустой эпизод и закрывает собственные устройства. Abort сохраняет текущий эпизод как incomplete. Если достигнуто выбранное число эпизодов, сессия закрывается. Start того же датасета добавляет новую сессию; Next в паузе сохраняет текущий session_id. Число `51` интерпретируется как 51, дробные значения отклоняются.

Начало аппаратной записи требует `explicit_user_start=true`, проверки занятости всех четырёх устройств и общего flock `hardware`. Повторная проверка выполняется непосредственно перед каждым open. Для servo tty после открытия устанавливается Linux TIOCEXCL; он не позволяет другому обычному процессу открыть уже занятый tty. Старые контроллеры не обязаны соблюдать наши advisory locks; поэтому проверка `/proc` владельцев обязательна. В ходе разработки реальные устройства не открывались.

Сохранён самостоятельный snapshot motor calibration в `config/calibration_snapshots`, включая исходный путь, SHA-256, mtime и версию LeRobot. Он считается неприменённым до readback: при старте значения в моторах сравниваются со snapshot; несовпадение останавливает подключение до enable torque. Калибровка моторов и camera geometry — разные контракты. Top/wrist geometry и hand-eye остаются unknown: камеры перемещались, ранее полученный RMSE не переносится на эту установку.

Подключение не вызывает stock `configure()` или `calibrate()`: они меняют настройки моторов и могут повторять записи. Новый адаптер проверяет Position mode, отключает torque, записывает текущую измеренную позицию как Goal_Position и только затем включает follower torque. Leader torque отключается. Никаких автоматических записей калибровки, PID, acceleration, autofocus, exposure или white balance нет. После явного Start выбирается 640×480, 30 FPS: top MJPG, wrist YUYV. У этой wrist-камеры MJPG 640×480 даёт readback около 120 FPS и не подходит для проверяемого режима. Формат/FPS/размер считываются обратно; несовпадение отменяет подключение. Уже совпадающие stream settings повторно не записываются. Проверяется получение минимум двух кадров за 3 секунды и свежесть обеих камер непосредственно перед разрешённым включением torque. Прямых записей camera controls нет. Readback focus/autofocus/exposure/white balance сохраняется до и после выбора потока. Если драйвер сам изменил значение при смене stream mode, это отмечается в controls_changed_by_driver; автоматического восстановления controls нет.

Каждый action — один фактически переданный, квантованный Goal_Position, после пределов калибровки и software limits. В human teleop delta/скорость ограничивают первоначальное выравнивание, затем передаётся прямая цель leader; в autonomous policy ограничения сохраняются на каждом шаге. В sidecar сохранены raw ticks, ограниченные суставы, start/end отправки. Sync write не подтверждает получение каждым мотором: `action_acknowledged=false`, достижение позиции не выдумывается. Ошибка отправки завершает сессию; motion никогда не повторяется автоматически. Старый state (>500 ms) не допускается к движению. Stop до дренирования файловой очереди отдельно пытается снять torque с каждого мотора (каждая write с num_retry=0). Ошибка одного Torque_Enable не отменяет попытки для остальных моторов. Port закрывается с disable_torque=False, чтобы SDK не запускал скрытые повторы. Ошибки сохраняются, повторный close возвращает тот же результат без новых bus writes. Ошибка отключения даёт статус torque_disable_unconfirmed_operator_check_required, а не ложное подтверждение отключения.

Камеры читаются отдельными потоками. Для observation выбирается только последний кадр с host monotonic read-end <= завершения чтения follower state. Это причинная привязка, а не аппаратная синхронизация экспозиции: exposure timestamp отсутствует и явно invalid. Контракт хранит:

- state read start/end и state timestamp, отправку action start/end;
- отдельный sequence, timestamp и read interval обеих камер;
- lossless PNG из декодированного RGB, SHA-256 и относительный путь;
- reuse/drop counters, camera age, control lateness и writer latency;
- измеренный joint/gripper position в degrees/% calibrated range;
- velocity/current/load/force и неразмеченные phase/success/done/grasp = unknown/invalid.

Камера, задержанная более чем на 100 ms по умолчанию, потеря изображения, нечисловые суставы или переполнение bounded queue останавливают управление. PNG encoding/fsync выполняет отдельный поток; SAM не импортируется и не запускается в loop. При сохранении используются `.partial`, drain очереди, fsync PNG/frames manifest и atomic rename в `episodes`. Ошибки/обрыв сервера отправляют доступные данные в `quarantine`. Восстановление не трогает `.partial` живого writer (проверяются PID и Linux process start ticks).

Ограничения: host timestamps не являются временем экспозиции; USB/MJPG транспорт камеры уже может быть сжат с потерями. Поток сохранения не делает аппаратную систему hard realtime. Software joint limits не доказывают отсутствие столкновений с внешними предметами; требуется оператор, доступный физический STOP и контрольный медленный эпизод. Физический STOP кнопкой на Mac зависит от сети, не заменяет аварийное отключение питания.

Проверки: `PYTHONPATH=src .venv/bin/python -m pytest -q tests/test_recording.py tests/test_recording_hardware.py` — 33 passed (при финальной приёмке 2026-11-06); совместно с tests/test_resources_jobs.py — 39 passed за 5.70 s. Проверены тестовый источник, lifecycle/add/re-record, сохранность отвергнутых данных, hashes/causality, число 51, disk/busy/error/restart, quantized sent action, single send без retry, stale state и absolute measured state gates, snapshot provenance. Аппаратное подключение/torque/частота/реальная синхронизация не проверялись из-за владельцев устройств.

Первичные сведения: [LeRobot SO-101](https://huggingface.co/docs/lerobot/so101), [код SOFollower v0.6.1](https://github.com/huggingface/lerobot/blob/v0.6.1/src/lerobot/robots/so_follower/so_follower.py). Реальные API и особенности sync_write сверены также с read-only установленным исходным кодом LeRobot 0.6.1; runtime зависимости используют только независимую среду лаборатории.


Приёмка файлов и финализация доступны как `finalize_dataset_path(path, allow_test_data=False, progress=None, stop=None)` без создания RecordingManager. Функция берёт dataset lease и не импортирует model/torch, не открывает камеры или servo bus. Проверяются schema/units, принадлежность session/episode, hash manifest и каждого PNG, декодируемость RGB, frame IDs, причинные интервалы state→observation→action, обе камеры, sequence/reuse/drop counters, FPS/границы эпизодов, membership hash и calibration readback provenance для hardware. Результат записывается атомарно в `validation/raw-validation.json`, а dataset metadata получает lifecycle_status finalized или validation_failed. При добавлении записи прежняя финализация становится stale_after_recording, датасет снова draft.

Это проверка сохранённых файлов: report всегда содержит software_only=true и hardware_verification=NOT_TESTED_BY_FILE_VALIDATOR. Synthetic требует явного allow_test_data и всегда training_eligible=false. Quarantine сохраняется и исключается. Ошибка проверки не превращается в успешную финализацию: вызывающий job обязан проверить report.finalized.

Новые regression tests проверяют настоящий установленный SDK LeRobot/Feetech при подменённом конечном _sync_write (Serial.open запрещён): квантование degrees и calibrated gripper %, raw ticks и отсутствие write retry. Отдельные fault tests покрывают частично успешный Torque_Enable, отключение всех моторов после первого отказа, cancellation startup, stale/future/invalid state, опасный policy action, STOP до/во время медленного drain, сохранение живой .partial, повреждённый RGB, будущий кадр, неизвестную сессию и повторную запись после finalized. Камерные regression tests используют подставной VideoCapture и не являются физической проверкой: они подтверждают выбор top MJPG / wrist YUYV, отказ при ошибочном FPS и отсутствие controls writes. Реальные camera/bus read-only результаты ведёт основной агент отдельно; реальные torque/направления/частота телеоперации требуют оператора.

Отдельный режим проверки рук (`capture_cameras=False`) получает только servo lease и не создаёт CameraCapture. CameraPreview использует отдельную cameras lease. Обычный raw recorder/inference по-прежнему получают обе lease и требуют свежие синхронные кадры. В runtime diagnostics раздельно сохраняются leader_requested, sent_action, measured_joints и tracking_error; это не дополнительные сенсоры.
