# Каталог задач опыта06 и составные задачи05

`explorer.skill_catalogue` — программный каталог и immutable пользовательские намерения. Он не обучает модель, не преобразует датасет и не открывает камеру/робота. Данные состояния в проверках существуют только во временных SQLite. Опыты02 и06 имеют разные robot/action contracts; каталог не объединяет их.

## Предложения и маршрутизация

`catalogue()` возвращает шаблоны опыта06: взять предмет в контейнер (включая «взять конфетку и положить в коробку»), взять из места, положить удерживаемый предмет в контейнер/ячейку, A→B, push→cell, sort по классу/цвету, stack при подтверждённой геометрии. Ведущая SO101 показывает, ведомая SO101 — целевой робот. Контракт `so101_follower_calibrated_position6_v1`: шесть фактических NAMES/UNITS из существующего `so101_station`, включая gripper. Это не сокращённый контракт ROSMASTER.

`propose_skill(text='', template_id=None)` выдаёт PROPOSED с owner_experiment, распознанным типом, robots, object/source/goal/recipient queries, фазами, сенсорами, demo plan, success, execution_method и missing_facts. Русский literal pattern — предложение с явной неопределённостью, которое оператор редактирует и подтверждает. Неизвестный текст не подтверждается до выбора шаблона/предмета/цели. ACT получает per-skill данные; текст — metadata SkillSpec, не language input ACT.

«дать мне печенье, которое привёз ROSMASTER» → owner05, composite parent и две закреплённые версии subskills02/06. В таком parent нет общего action vector; dataset merge и concatenation9+6 запрещены. Подтверждение требует реальные confirmed child SkillSpecs, точные UUID/version/spec SHA и правильные embodiment contracts. Release guard требует независимое source-bound person-grasp evidence; timer/VLM не подтверждают контакт. Другой явно ROSMASTER-запрос принадлежит02 и направляется к его отдельному unified workflow. Выбор шаблона06 явно задаёт владельца06; это не автоматический перевод произвольного текста в моторную команду.

`create_proposal(store,{text,template_id,request_id})` сохраняет stable UUID/v1 в существующие immutable events. Retry с тем же intent идемпотентен; изменённый intent с тем же request_id отвергается. `revise_proposal(store,id,version,patch,spec_sha256)` создаёт линейную следующую версию; ownership/contracts/physical constraints нельзя редактировать. `confirm_proposal(...,known_specs=[])` подтверждает точный SHA. Для05 known_specs — server-owned подтверждённые записи02/06, не произвольные клиентские receipts. `list_proposals(store)` возвращает все версии. Миграции БД не нужны.

## Показы и отдельная готовность

`demonstration_plan(spec, episode_reports, receipt_verifier=...)` считает технический начальный план3train+1development+1sealed, phase×variant, целые/targeted/recovery показы, причины отклонений и номер следующей попытки. Duplicate original ID не увеличивает охват. Failed/unknown не превращаются в экспертные цели; targeted не заменяет whole. После начального охвата предлагается независимая learned-policy проверка, а не заявляется мастерство. Planner не квалифицирует dataset и не заменяет глобальный split checker: trusted server verifier обязан проверять исходное provenance и независимость разделов. Без verifier все входные reports неподтверждены. Sealed данные не выбираются для исправления/оптимизации.

`readiness(spec,confirmed=False,receipts={},receipt_verifier=None)` отдельно показывает template/demos/trained/shadow/physical. Пользовательские booleans даже с правильным SHA не являются доказательством. Без trusted server callback ни один evidence stage не становится ready. Callback `(kind,receipt,spec)->bool` должен читать фактические immutable job/artifact receipts; его нельзя заменить полем HTTP request. Readiness проверяет skill/version/owner/action contract, aggregate/model lineage; trained требует действительный receipt официального LeRobot0.6, shadow — свежие наблюдения без dispatch, physical — отдельный наблюдаемый пользователем настоящий physical learned-policy test с независимым полным результатом. Raw episode replay не learned rollout. SIM trained/shadow не подтверждают physical.

Планируемый отдельный data backend — `explorer_sim.so101_dataset_qualification`, владелец другой агент/integrator. Наличие имени в каталоге не утверждает, что backend уже выполнился. Требуемая запись06 сохраняет leader measured, follower requested/accepted/dispatched/measured и маски, camera identity/calibration, clocks/boot/mappings, выбор предмета/цели и независимые phase/full outcomes. Legacy hold без object attainment остаётся trajectory/analysis; старые данные не удаляются. Отдельная квалификация установленного LeRobot0.6.1 обнаружила default degrees у официального SO follower против исходных normalized6D станции, а стандартный robot.connect/configure пишет настройки моторов. Поэтому catalogue не разрешает default hardware connect; dataset readback не квалифицирует replay/controller path. Физический этап требует отдельного доказательства правильных координат, проверенного native executor и сохранённых исходных настроек. Official dataset readback, техническая пригодность, полнота teaching provenance и object expert eligibility должны сообщаться отдельно.

Ни `template.ready`, ни полный readiness не выдаёт разрешение на новое движение: `physical_execution_authorized=False`. Обе руки остаются неподвижны без отдельного user-observed теста; шасси запрещено перемещать; настройки контроллеров сохраняются.

## UI hooks

Новый независимый `static/skill-catalogue.js` не содержит network/motor IO. `skillCataloguePanel({catalogue,selected,readiness,available_child_specs,references_validated})` рисует owner/robots/query/phase/sensor/demo/method и редактируемые поля. Root должен передавать фактическое server state и подключить forms `skill-catalogue-propose`, `skill-catalogue-edit`, кнопку `data-catalogue-action=confirm` к backend-функциям. `skillCatalogueEditPatch(form,spec)` возвращает task patch и pinned child refs. Пока parent API не подключён, этот компонент не заявляется работающей live страницей. Root владеет app/routes/station.js и legacy06 aliases.

## Программная проверка

`pytest tests/test_skill_catalogue.py -q` — только source/temp fixtures. Проверяет06vs05 routing,6Dvs9D contracts, Russian candy proposal, stable versions/references, readiness stage separation, replayvsrollout/SIM semantics, partial/failure/unknown/duplicate coverage. `node --check .../skill-catalogue.js` проверяет синтаксис; Node VM проверяет actual renderer и отсутствие автоматического network/motor path. Никаких физических проб эти проверки не выполняют.
